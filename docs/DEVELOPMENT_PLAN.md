# SmartCare 知识助手开发计划

## 1. 当前基线

| 项目 | 内容 |
|---|---|
| 根目录 | 仓库根目录 |
| 初始提交 | `9438fbf chore: initialize SmartCare monorepo` |
| 远程仓库 | 暂未配置 |

| 复杂会话管理 | 不实现 |
| 暂不纳入领域 | 医保、系统手册、设备 |

## 2. 阶段计划

| 阶段 | 目标 | 主要产出 | 完成标志 |
|---|---|---|---|
| 0 | 仓库与文档基线 | 文档目录、基线标签、开发规则 | 工作区干净，基线可检出 |
| 1 | 知识模型与领域注册 | 通用文档模型、领域注册、统一响应 | 药品回归不退化 |
| 2 | 文档导入与索引 | 解析、切片、Embedding、Catalog 发布 | 可生成并验证独立索引版本 |
| 3 | 检索接口与服务接入 | FastAPI、Spring Boot 代理、错误映射 | 端到端问答链路可用 |
| 4 | 管理端功能 | 助手抽屉、管理菜单、文档和任务页面 | 前端状态和接口联调通过 |
| 5 | 新增知识域 | 制度、检查注意事项、健康宣教 | 各领域独立检索和评测 |
| 6 | 联调与验收 | Compose、异常、持久化、回归测试 | 验收记录完成 |

## 3. 每阶段规则

阶段开始前明确目标、范围、不包含内容和验收标准，并确认当前基线。

阶段结束时执行构建、测试或手工验证，将实际结果写入 `docs/acceptance/`，使用小提交记录改动，并创建阶段标签，例如 `phase/1-knowledge-model`。

## 4. 提交约定

提交格式：`type(scope): description`。

允许的 `type`：`feat`、`fix`、`refactor`、`test`、`docs`、`chore`。

示例：

```text
feat(rag): add knowledge domain registry
test(rag): add drug retrieval regression cases
docs(plan): record phase one acceptance result
```

一个提交只解决一个明确目标；跨模块改动需要在提交说明或验收文档中说明原因。

## 5. 成功标准

- 能从基线标签重现阶段开始状态；
- 能通过提交记录定位每项功能的实现范围；
- 能从验收记录确认测试命令和实际结果；
- 未实现的设计、配置和接口不会被写成已完成能力；
- 生成数据、真实密钥和本地依赖不进入 Git。
